# HTTP Method

_2026.11.16._

> 클라이언트가 서버에 보내는 요청의 첫 줄에 담기는, 대상 리소스에 어떤 동작을 할지 나타내는 값

- 인터넷 표준 기구(IETF)에 의해 정해진 것으로, 어떤 서버·클라이언트에서든 같은 의미를 기준으로 사용된다.

```http
POST /posts HTTP/1.1                  ← request line
Content-Type: application/json        ← header

{"title": "첫 글"}                     ← body
```

> 단순화한 HTTP 요청 메시지 예시.

## GET

- 서버에 있는 데이터를 가져오는 요청이다.

```http
GET /posts/1 HTTP/1.1
```

```http
HTTP/1.1 200 OK

{"id": 1, "title": "첫 글"}
```

> 1번 게시글을 요청하고, 서버가 `200 OK`와 함께 데이터를 돌려준다.

- GET은 특정 주소에 있는 데이터를 달라는 요청이기 때문에 서버에 별도로 전달할 데이터가 존재하지 않는다. 즉 **body를 사용하지 않는다.**

```ts
fetch("/posts", { method: "GET", body: JSON.stringify({ page: 2 }) });
// TypeError: Request with GET/HEAD method cannot have body.
```

> fetch의 경우 GET에 body를 넣으면 요청을 보내기도 전에 바로 에러를 낸다!

- 요청하는 데이터에 추가 조건이 있을 경우 쿼리스트링을 사용하여 표현한다.

```ts
fetch("/posts?page=2&sort=latest"); // fetch 사용
axios.get("/posts", { params: { page: 2, sort: "latest" } }); // axios 사용 - 결과적으로 위와 같은 URL이 만들어진다.
```

> **쿼리스트링(Query String)**  
> URL 끝에 `?` 뒤로 `키=값`의 형태로 이어 붙여 서버에 추가 조건을 전달하는 부분. 여러 개일 경우 `&`로 연결한다.  
> 쿼리스트링은 body와 달리 그대로 URL에 포함되어 서버 로그 등에 기록이 남으므로 비밀번호·토큰과 같은 민감한 값은 넣으면 안 된다.

## POST

- 새 데이터를 만드는 요청이다.
- 만들 데이터의 내용을 body에 담아 보낸다.

```http
POST /posts HTTP/1.1
Content-Type: application/json

{"title": "첫 글"}
```

```http
HTTP/1.1 201 Created

{"id": 1, "title": "첫 글"}
```

> 데이터 생성에 성공하면 주로 `201 Created`가 오고, 서버가 붙인 `id`를 포함하여 생성된 데이터를 돌려주기도 한다.

- 꼭 데이터 생성이 아니더라도 GET, PUT, PATCH, DELETE 중 어디에도 맞지 않는 요청은 POST를 사용한다.  
  _EX) 로그인(`POST /auth/login`). 데이터 생성은 아니나 이메일, 비밀번호를 body에 담아야 하기 때문에 GET은 사용할 수 없다._

## PUT

- 이미 존재하는 데이터를 보낸 body의 내용으로 **통째로 바꾸는** 요청이다.
- URL에 변경할 데이터의 id를 넣어 지정한다. _EX) `PUT /posts/1`_

## PATCH

- 이미 존재하는 데이터에서 body에 넣어 보낸 **특정 필드만 고치는** 요청이다.
- URL에 변경할 데이터의 id를 넣어 지정한다. _EX) `PATCH /posts/1`_

## DELETE

- 데이터를 삭제하는 요청이다.
- URL에 삭제할 데이터의 id를 넣어 지정한다. _EX) `DELETE /posts/1`_
- 성공 응답은 서버에 따라 주로 아래 두 가지 중 하나이다.
  - `200 OK`: 삭제된 데이터 또는 결과 메시지를 body에 담아 준다.
  - `204 No Content`: 별도 body 없이 삭제 성공을 의미하는 상태 코드만 준다.

## PUT vs PATCH

- 둘 다 데이터를 수정하는 요청이지만, 같은 body를 보냈을 때 그 결과에 차이가 있다.

```json
{ "name": "영핑이", "email": "a@a.com", "bio": "프론트엔드" }
```

> 서버에 저장되어 있는 기존 데이터 예시.

- 여기에 body에 `{ "name": "나영" }`을 담아 보내는 경우의 각 결과는 아래와 같다.

```json
{ "name": "나영" }
```

> PUT: 보낸 body의 내용으로 데이터 전체를 교체하므로, `email`, `bio`가 사라진다.

```json
{ "name": "나영", "email": "a@a.com", "bio": "프론트엔드" }
```

> PATCH: body에 담아 보낸 `name`만 바뀌고, 나머지 필드는 그대로 유지된다.

## HEAD

- GET과 동일한 요청이나 응답에서 body를 빼고 헤더만 받는다.
- 용량이 큰 파일을 내려받기 전 `Content-Length` 헤더로 크기만 확인하거나 또는 데이터가 존재하는지만 확인할 때 사용한다.

## OPTIONS

- 해당 URL에서 서버가 허용하는 메서드, 헤더 등 통신 옵션을 확인하는 요청이다.
- 프론트엔드에서 직접 보낼 일은 거의 없고, 주로 [CORS Preflight](./CORS.md#preflight-request) 과정에서 브라우저가 본 요청 전에 자동으로 보낸다. ([사전 요청 흐름](./CORS.md#사전-요청-흐름) 참고)

## 안전성·멱등성

- 메서드마다 가진 성질 두 가지로, 이 성질들에 따라 요청의 재시도·캐시 여부 등이 결정된다.

| 메서드  | 안전 | 멱등 |
| :-----: | :--: | :--: |
|   GET   |  O   |  O   |
|  POST   |  X   |  X   |
|   PUT   |  X   |  O   |
|  PATCH  |  X   |  X   |
| DELETE  |  X   |  O   |
|  HEAD   |  O   |  O   |
| OPTIONS |  O   |  O   |

### 안전성(Safe)

- 요청을 보내도 서버의 데이터가 바뀌지 않는다.
- 조회만 하는 GET, HEAD, OPTIONS가 해당된다.

> **캐시**  
> GET은 서버 데이터를 바꾸지 않으니, 매번 서버에 요청하지 않고 캐싱해둔 응답을 써도 문제가 없다. 따라서 브라우저는 GET 응답을 캐싱한다.

### 멱등성(Idempotent)

- 동일한 요청을 보내는 횟수와 관계없이 서버 데이터의 최종 결과가 동일하다.
- GET: 조회만 하니 몇 번을 요청해도 데이터는 그대로이다. **멱등**
- POST: 요청을 보낼 때마다 데이터가 생성된다. 멱등이 아니다.
- PUT: 동일 body로 여러 번 요청해도 결과는 동일하다. **멱등**
- DELETE: 첫 요청에서 데이터가 삭제된 후, 두 번째 요청부터는 존재하지 않는 데이터이니 `404` 에러가 발생할 수 있다. 그러나 해당 데이터가 삭제되었다는 상태는 일관되게 유지된다. **멱등**
- PATCH: 일반적으로 PUT과 같이 동일 값을 덮어쓰나, 요청을 보낼 때마다 값이 바뀌게 만들 수도 있다. 즉 멱등이 보장되지 않는다.

  ```http
  PATCH /posts/1 HTTP/1.1

  {"op": "increment", "field": "likeCount"}
  ```

  > 좋아요 수를 1 증가시키는 요청. 요청을 보낼 때마다 1, 2, 3으로 값이 증가한다.

> **재시도**  
> 요청을 보냈는데 네트워크가 끊겨 응답이 오지 않는 경우, 클라이언트는 서버가 요청을 정상 처리했는지 알 수 없다.  
> GET, PUT, DELETE는 처리 여부를 몰라 요청을 다시 보내더라도 요청이 한 번 처리된 상태와 같아지므로 재시도해도 된다.
